# Testing without a GPU

Three ways to put accelerators in front of the plugin on a laptop, from
"no cluster at all" to "a real scheduler handing out fake H100s". None of
them needs a GPU.

| | What you get | Needs |
| --- | --- | --- |
| `npm run preview` | every page, drawn against `src/fixtures.ts`, in the light and dark themes | Node |
| `dev/kind-dra.sh` | a kind cluster with the DRA example driver's 8 simulated GPUs and sample workloads | docker, kind, kubectl, helm, git |
| `dev/kwok-fleet.sh` | 10 fake GPU nodes (KWOK) — 48 H100s, a MIG node, L4 and time-sliced T4 nodes — with workloads | kind, kubectl, node |

Both scripts create or reuse one kind cluster, `gpu-dra`, so running
`kind-dra.sh` and then `kwok-fleet.sh` gives you both in one cluster. kind
adds the context `kind-gpu-dra` to your kubeconfig and makes it current;
every command in the scripts names that context explicitly, so no other
cluster is touched. Open `kind-gpu-dra` in K8s Dockside to see the plugin
against it.

## 1. The preview: no cluster

```sh
npm install
npm run preview   # writes preview/, open preview/index.html
```

`src/fixtures.ts` mirrors both setups below, and adds the states a cluster
rarely shows on demand: a tainted device, a node that lost a GPU, a daemonset
not ready, a claim nobody uses, both paths advertising the same cards. The
render test (`npm run test`) asserts on the same fixtures.

## 2. `kind-dra.sh`: simulated GPUs through DRA

```sh
dev/kind-dra.sh          # create gpu-dra, install the driver and the workloads
dev/kind-dra.sh delete   # delete the cluster
```

[kubernetes-sigs/dra-example-driver](https://github.com/kubernetes-sigs/dra-example-driver)
is the Kubernetes project's reference DRA driver. It publishes 8 fake GPUs
per worker (driver and DeviceClass `gpu.example.com`, model
`LATEST-GPU-MODEL`, 80Gi each) in a ResourceSlice and allocates them to
claims like any real driver; the containers get environment variables
instead of a device.

The script follows the driver's README (a kind cluster, then its Helm chart),
with two differences: it installs the image the project publishes at
`registry.k8s.io/dra-example-driver/dra-example-driver:v0.5.0` instead of
building one, and it takes the chart from a shallow clone of the `v0.5.0`
tag (cached in `dev/.cache/`). The node image is `kindest/node:v1.37.0`, the
one the driver's own demo uses at that tag; DRA is GA from 1.34, so no
feature gates are set. Override with `NODE_IMAGE=`, `DRIVER_REF=` and
`CLUSTER=`.

Then it applies [`manifests/dra-workloads.yaml`](manifests/dra-workloads.yaml)
in namespace `dra-demo`:

| Pod | Asks for | What you should see |
| --- | --- | --- |
| `single-gpu-pod` | 1 GPU, from a claim template | one blue square |
| `two-gpu-pod` | 2 GPUs in one request | two blue squares, one claim |
| `shared-a`, `shared-b` | the ResourceClaim `shared-gpu` | one striped square, "Shared by 2 pods" |
| `too-many-gpus-pod` | 16 GPUs | Pending, and "can never fit: asks for 16, the biggest node has 8" |
| — | the claim `spare`, no pod | a pending claim, explained as waiting for a pod |

## 3. `kwok-fleet.sh`: a fleet at scale

```sh
dev/kwok-fleet.sh          # install KWOK and the fleet into gpu-dra (creating it if needed)
dev/kwok-fleet.sh delete   # remove the fleet; the cluster stays
```

[KWOK](https://kwok.sigs.k8s.io) keeps Node objects Ready and "runs" pods
scheduled onto them, with no kubelet. The script installs KWOK `v0.8.0` the
way its "kwok in cluster" guide does (`kwok.yaml` and `stage-fast.yaml` from
the release), then applies [`manifests/kwok-fleet.yaml`](manifests/kwok-fleet.yaml):

| Node | Accelerators | Path |
| --- | --- | --- |
| `h100-node-1` … `-6` | 8 × H100 80GB HBM3 each, with NVIDIA-style attributes | DRA, driver `gpu.nvidia.com` |
| `a100-mig-node` | 4 × A100 80GB: seven 1g.10gb instances on gpu-0, 3g + 2g + 2g on gpu-1, two whole | DRA, static MIG |
| `l4-node-1`, `l4-node-2` | 4 × L4 each; l4-node-2 has lost one (allocatable 3) | device plugin, `nvidia.com/gpu` |
| `t4-ts-node` | 2 × T4, time-sliced 4 ways (`nvidia.com/gpu: 8`) | device plugin, GFD replica labels |

plus DeviceClasses `gpu.nvidia.com` and `mig.nvidia.com` (with the CEL
selectors NVIDIA's chart installs) and, in namespace `gpu-fleet`: two 8-GPU
training pods, five single-GPU pods, a claim shared by two pods, four MIG
notebooks, device-plugin pods on the L4 and T4 nodes, `llama-finetune`
waiting for 4 L4s, and `too-big-to-fit` asking for 16 H100s.

There is no driver behind these slices: the scheduler allocates their
devices to claims as usual, and nothing ever prepares them on a node — which
KWOK does not need. The manifest is generated by
[`kwok/fleet.mjs`](kwok/fleet.mjs); change that and regenerate:

```sh
node dev/kwok/fleet.mjs yaml > dev/manifests/kwok-fleet.yaml
```

A Node's status is a subresource, so `kubectl apply` writes it only when the
node is created; the script patches each node's status afterwards
(`node dev/kwok/fleet.mjs status` prints the patches) so the GPUs are right
on a second run too.

## 4. Charts: fake DCGM metrics

The dashboard's utilisation and memory charts read NVIDIA's DCGM exporter
metrics (`DCGM_FI_DEV_GPU_UTIL`, `DCGM_FI_DEV_FB_USED`, …) from the cluster's
Prometheus. Without one they say so and nothing else changes.

To see them filled in without a GPU, run.ai's
[fake-gpu-operator](https://github.com/run-ai/fake-gpu-operator) simulates
GPUs on CPU-only nodes — the device plugin, feature discovery and an
exporter included — driven by pod annotations such as
`run.ai/simulated-gpu-utilization: "10-30"`. Its exporter writes
`DCGM_FI_DEV_GPU_UTIL`, `DCGM_FI_DEV_FB_USED` and `DCGM_FI_DEV_FB_FREE` with
the `Hostname`, `modelName`, `gpu` and `pod` labels the plugin's queries use
(checked in its source); it has no power or temperature, so those two charts
stay empty. Its README has the install
(label the nodes `run.ai/simulated-gpu-node-pool=default`, then its Helm
chart from `oci://ghcr.io/run-ai/fake-gpu-operator`), and it needs a
Prometheus scraping it, such as kube-prometheus-stack. It runs real pods, so
use it on the kind nodes, not the KWOK ones.

## What has and has not been checked

- Every manifest here, and every object in `src/fixtures.ts`, decodes
  strictly (unknown fields rejected) into the `k8s.io/api` v0.37 Go types.
- The KWOK node attribute and label names are checked against the NVIDIA DRA
  driver's and gpu-feature-discovery's source; the values are made up.
- The scripts were written against the driver's `v0.5.0` tag and KWOK's
  `v0.8.0` release, whose files and deployment names were checked. They have
  **not** been run end to end by the plugin's author on the machine it was
  written on (docker could not network containers there), so if a step
  fails, the output says which one.
